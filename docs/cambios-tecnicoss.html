1 · Implementación de DTOs

Los Data Transfer Objects (DTOs) son objetos que definen la forma exacta de los datos que entran y salen de cada capa de la aplicación. Su propósito es separar los modelos internos de base de datos del contrato público de la API.

Problema anterior Los controllers tenían los schemas de validación Zod duplicados. Los services retornaban tipos crudos de Prisma directamente al cliente, lo que podía exponer campos sensibles como password, y no había contratos explícitos entre capas.
Solución aplicada Se creó la carpeta src/dtos/ con dos archivos: auth.dto.ts y message.dto.ts. Cada uno centraliza los schemas de validación de entrada y las interfaces de salida, junto con funciones mapper que convierten modelos Prisma en DTOs.

auth.dto.ts — nuevo

// Request — schema de validación Zod (compartido entre register y login)
export const authRequestSchema = z.object({
  username: z.string().min(3),
  password: z.string().min(6),
});

// Response — el usuario nunca expone su contraseña
export interface AuthUserResponseDto {
  id:       string;
  username: string;
  role:     Role;
}

// Mapper: convierte el modelo Prisma User → DTO seguro
export const toAuthUserResponse = (
  user: Pick<User, 'id' | 'username' | 'role'>
): AuthUserResponseDto => ({
  id: user.id, username: user.username, role: user.role,
});

message.dto.ts — nuevo

// Request — envío de mensaje
export const sendMessageRequestSchema = z.object({
  content:   z.string().min(1),
  platforms: z.array(z.nativeEnum(Platform)).min(1),
});

// Request — filtros de consulta (convierte strings a Date automáticamente)
export const messageFiltersSchema = z.object({
  status:   z.nativeEnum(MessageStatus).optional(),
  platform: z.nativeEnum(Platform).optional(),
  from:     z.coerce.date().optional(),
  to:       z.coerce.date().optional(),
});

// Response — forma pública del mensaje (sin datos internos de BD)
export interface MessageResponseDto {
  id:         string;
  content:    string;
  createdAt:  Date;
  deliveries: DeliveryResponseDto[];
}

2 · Corrección — métricas sin usuarios sin mensajes

Bug identificado El endpoint GET /messages/metrics no mostraba usuarios que nunca habían enviado un mensaje. La función getAdminMetrics() construía el mapa de resultados iterando mensajes, por lo que los usuarios sin mensajes nunca aparecían en la respuesta.

Causa raíz

// ❌ Antes — el mapa se construye desde mensajes
const messages = await getAllMessages();

for (const msg of messages) {
  // Si un usuario no tiene mensajes, nunca entra acá → no aparece en el resultado
  if (!metricsMap[msg.userId]) {
    metricsMap[msg.userId] = { username: msg.user.username, total: 0, todayCount: 0 };
  }
}

Corrección aplicada

// ✅ Ahora — se parte desde todos los usuarios
const [users, messages] = await Promise.all([getAllUsers(), getAllMessages()]);

// Todos los usuarios entran al mapa con total 0
const metricsMap = Object.fromEntries(
  users.map((u) => [u.id, { username: u.username, total: 0, todayCount: 0 }])
);

// Los mensajes suman sobre el mapa ya existente
for (const msg of messages) {
  const entry = metricsMap[msg.userId];
  if (!entry) continue;
  entry.total++;
  if (msg.createdAt >= start) entry.todayCount++;
}

Archivos modificados

3 · RBAC — permisos en base de datos

RBAC (Role-Based Access Control) es un modelo de control de acceso donde los permisos se asignan a roles, y los roles a usuarios. Implementarlo en base de datos permite modificar permisos sin necesidad de cambiar código ni hacer deploy.

Problema anterior Los permisos estaban hardcodeados en authorize.ts como un objeto literal. Cualquier cambio (nuevo permiso, nuevo rol, revocar acceso) requería modificar el código fuente y redesplegar la aplicación. 
// ❌ Antes — permisos quemados en el código
const ROLE_PERMISSIONS: Record<string, string[]> = {
  ADMIN: ['*'],
  USER:  ['messages:create', 'messages:read'],
};

Nuevos modelos en el schema de Prisma

model Permission {
  id          String  @id @default(uuid())
  name        String  @unique          // ej: "messages:create"
  description String?

  rolePermissions RolePermission[]
}

model RolePermission {
  role         Role
  permissionId String
  permission   Permission @relation(fields: [permissionId], references: [id], onDelete: Cascade)

  @@id([role, permissionId])
}

Middleware authorize — con cache en memoria

// Cache cargado una vez desde BD. Se invalida llamando clearPermissionsCache().
let permissionsCache: Map<string, Set<string>> | null = null;

const loadPermissions = async () => {
  if (permissionsCache) return permissionsCache; // usa cache

  const rows = await getAllRolePermissions();     // consulta BD una sola vez
  const cache = new Map<string, Set<string>>();

  for (const row of rows) {
    if (!cache.has(row.role)) cache.set(row.role, new Set());
    cache.get(row.role)!.add(row.permission.name);
  }

  permissionsCache = cache;
  return permissionsCache;
};
¿Cómo funciona el cache? En el primer request que requiera autorización, el middleware consulta la BD y guarda los permisos en memoria. Todos los requests siguientes usan ese mapa sin tocar la BD. Si se modifican permisos en la BD, se puede llamar a clearPermissionsCache() para forzar una recarga.

5 · Comandos para aplicar los cambios

Ejecutar los siguientes comandos con la base de datos corriendo:

# 1. Aplicar la migración de RBAC a la BD
npx prisma migrate deploy

# 2. Poblar los permisos y el usuario admin
npx tsx src/seed.ts

# 3. Levantar el servidor
npm run dev
Nota El cliente de Prisma ya fue regenerado con prisma generate, por lo que los nuevos modelos Permission y RolePermission ya están disponibles en el código TypeScript.
